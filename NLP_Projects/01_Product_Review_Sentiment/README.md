# Product Review Sentiment

**Methods practised:** NLP fundamentals (Batch 2 Module 07): text cleaning, tokenisation, bag-of-words / TF-IDF,
word and character n-grams, linear text classifiers (Logistic Regression, Linear SVM, Multinomial Naive Bayes),
negation handling and explaining predictions with word weights. Also uses stratified cross-validation, macro-F1 and
`GridSearchCV` (model evaluation) and serving a saved model behind a Flask API (Module 13).

## Problem statement

ShopKart, a fictional e-commerce company, receives thousands of product reviews every week. The product team wants each
review **automatically tagged as positive, neutral or negative**, and wants to see **which words drove each tag**, so they
can trust the result and spot recurring complaints such as "battery dies fast" or "size runs small".

**Expected result:** a TF-IDF + linear classifier that is far better than a "always say positive" baseline on
macro-F1, realistic (not perfect) performance with most confusion around the neutral class, an honest error analysis,
and an API + web page that analyses one review (with probability bars and highlighted words) or up to 50 at once.
(The build run's actual numbers are in `VERIFICATION.md` and the executed notebook.)

## Dataset

Synthetic reviews generated by `data/generate_data.py` for five product categories (electronics, clothing, home, beauty,
grocery). The text is built from many phrase pools and includes the things that make real reviews hard: negation
("not bad", "not worth it"), mixed opinions ("great screen but battery dies fast"), a little sarcasm, Hinglish words
("bahut accha", "bekaar"), emojis and typos. About 6% of labels were deliberately flipped (annotator mistakes), and the
file contains duplicates and empty reviews to clean. See [data/DATA_DICTIONARY.md](data/DATA_DICTIONARY.md).
The target column is `sentiment` (positive / neutral / negative); the model uses **only** `review_text`.

## What the notebook does

1. **Inspect and clean:** find missing and blank reviews and duplicate rows, and drop them.
2. **Explore:** class balance (imbalanced, so we use macro-F1), rating vs label (shows label noise), review length,
   category mix, and how many reviews contain negation, contrast words, Hinglish and emojis.
3. **Clean the text** with `clean_text()` from `backend/text_utils.py`: lower case, emojis → words (`emo_pos`), expand
   "n't" → "not", squash repeated letters, drop punctuation. Stop words are **kept** (they include *not*, *no*, *but*).
4. **Stratified 80/20 split**, then **TF-IDF** explained on a tiny example.
5. **Compare** a majority-class baseline with Logistic Regression, Linear SVM and Multinomial NB, each with word
   unigrams, word 1–2 grams and char 2–5 grams, using stratified 5-fold CV (macro-F1 and accuracy).
6. **Tune** `C` for the chosen model: Logistic Regression + word 1–2 grams (it gives probabilities and readable weights).
7. **Negation experiment:** removing stop words vs keeping them vs adding bigrams, scored on reviews containing a negation.
8. **Test-set evaluation** (used once): classification report and confusion matrix.
9. **Error analysis:** the most confident mistakes (many are label noise) and error rates for contrast, negation,
   Hinglish and short reviews.
10. **Top words per class** and a per-review explanation (TF-IDF value × weight), the same method the API uses.
11. **New reviews and edge cases:** Hinglish, sarcasm, nonsense text, other domains.
12. **Save** the pipeline and `sentiment_info.json`, reload and check, then **limitations**.

## How to run (three terminals)

**1. Python environment and notebook** (from this project folder):

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate    macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
jupyter notebook notebook/Product_Review_Sentiment.ipynb     # Run All: this creates models/
```

The trained model is already included in `models/`, so you can skip straight to step 2 if you only want the app.

**2. Backend API** (same environment, from this project folder):

```bash
python backend/app.py                 # http://localhost:5000
python -m unittest discover -s backend -p "test_*.py" -v    # optional: run the tests
```

Try it without the frontend:

```bash
curl http://localhost:5000/api/health
curl -X POST http://localhost:5000/api/analyze -H "Content-Type: application/json" \
  -d '{"text": "Great screen but the battery dies fast."}'
curl -X POST http://localhost:5000/api/analyze-batch -H "Content-Type: application/json" \
  -d '{"texts": ["Love it, superb quality!", "Not worth it.", "It is okay."]}'
```

**3. Frontend** (needs Node.js 18+):

```bash
cd frontend
npm install
npm run dev                           # open http://localhost:5173
```

If the API runs somewhere else, copy `.env.example` to `.env` and change `VITE_API_URL`. If the frontend runs on a
different address, start the backend with `FRONTEND_ORIGIN=http://that-address python backend/app.py`.

## Architecture and request flow

```
 Browser (React)                       Flask API (backend/app.py)                       models/
 ───────────────                       ──────────────────────────                       ───────
 page opens ── GET /api/health ─────▶  model name, limits (loaded at start) ◀────────── sentiment_info.json
            ── GET /api/examples ───▶  example reviews for the buttons
 "Analyze"  ── POST /api/analyze ───▶  1. parse JSON (400 if not JSON)
   {text: "Great screen but ..."}      2. validate text (422: missing / not a string / empty / > 2000 chars)
                                       3. pipeline.predict_proba(text) ◀──────────────── sentiment_model.joblib
                                          (TF-IDF calls clean_text from text_utils.py)
                                       4. contribution of each term = TF-IDF value × class weight
            ◀── 200 {label, confidence, probabilities, top_terms, known_terms, cleaned_text}
 badge + probability bars + highlighted words

 Batch tab  ── POST /api/analyze-batch {texts: [...≤50]} ─▶ validate each line, ONE model call for the valid ones
            ◀── 200 {results: [per line], summary: {total, valid, invalid, counts}}
 summary boxes + table
```

- The model is **trained once in the notebook** and loaded **once when the API starts**. Requests only call the model.
- The saved object is the **whole pipeline**, and the TF-IDF step calls `text_utils.clean_text`, so the notebook and the
  API clean text identically. Keep `text_utils.py` next to `app.py`; joblib needs it to load the model.
- Logistic Regression gives **probabilities**, which is why it was chosen over the (slightly higher scoring) Linear SVM.
  Predictions below 0.5 confidence are flagged `low_confidence`, and `known_terms: 0` means no word was recognised.

### API reference

| Method | Path | Request | Success response | Errors |
|---|---|---|---|---|
| GET | `/api/health` | — | `{"status": "ok", "model", "labels", "test_macro_f1", "max_chars", "max_batch"}` | — |
| GET | `/api/examples` | — | `{"examples": ["...", ...]}` | — |
| POST | `/api/analyze` | `{"text": "..."}` | `{"label", "confidence", "low_confidence", "probabilities": {negative, neutral, positive}, "top_terms": [{"term", "weight"}], "known_terms", "cleaned_text", "model"}` | 400 body not JSON; 422 `{"error", "fields": {"text": message}}` |
| POST | `/api/analyze-batch` | `{"texts": ["...", ...]}` (1–50) | `{"results": [{"row", "ok", "text", ...analysis or "error"}], "summary": {"total", "valid", "invalid", "counts"}, "model"}` | 400 body not JSON; 422 not a list / empty / more than 50 |

Validation rules for a review: required; must be a string; not empty or only spaces; at most 2,000 characters; must
contain at least one letter or digit after cleaning. In a batch, invalid lines are reported per row and the valid ones
are still analysed.

`top_terms[].weight` is the term's contribution to the **predicted** label: positive = pushed towards it, negative =
pushed away from it.
